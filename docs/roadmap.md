## P0 · 安全与数据（公网部署前必须做）

### 1. 登录限流与失败锁定 — ✅ 已完成（2026-10-23）

**问题**：`POST /api/auth/login` 没有任何频率控制。密码是唯一的防线，
脚本可以全天候试错。当前密码虽已改强，但只要部署到公网，这就是最先被打的门。

**实际做法**（`LoginAttemptService` + `AuthController`，比重写前多了一层）：
- **两级计数**：`用户名 + IP` 满 5 次锁 15 分钟；`用户名`（跨 IP）满 15 次也锁。
  加第二层是因为 IP 来自 `X-Real-IP`，而它可伪造（绕过 nginx 直连 8081 就能乱填），
  只按 IP 计数等于换个头就重置。单机只有一个管理员账号，守住这一个账号就够了。
- 内存 `ConcurrentHashMap`：`compute` 保证并发下不丢计数；条目超过 1 万时清理过期项，
  防止被大量随机用户名刷爆内存。
- 锁定期间返回 **429 + `Retry-After`**，不是 401——前端对 401 的处理是清 token 跳登录页，
  「试太多次」不该触发那套逻辑。
- 窗口 15 分钟：过期后自动解除，不需要手工清理；登录成功后清零。
- 审计只写一条 `LOGIN_BLOCKED`（**不是每次被拒都写**，否则日志会被刷爆）。
- 用户名大小写不敏感，避免 `Admin` / `admin` 各算一份。

**已知边界**：状态在进程内存里，重启即清零；多实例部署时各实例各算各的，要共享存储才能统一。

**验收**：连续 6 次错误密码 → 第 6 次 429 且带 `Retry-After: 899`；15 分钟后恢复。
测试 `LoginAttemptServiceTest`（6 例）+ `AuthControllerTest`（2 例）。

### 2. 备份自动化 — ✅ 已完成（2026-10-23）

**问题**：`scripts/backup.sh` 已验证可恢复，但没有任何机制保证它真的在跑。
备份的最大风险不是"备不出来"，而是"三个月后才发现从没成功过"。

**实际做法**：
- `scripts/scheduled-backup.sh` + `scripts/com.notesblog.backup.plist`，每天 03:00 跑，
  日志 `~/Library/Logs/notesblog-backup.log`；睡眠时唤醒后补跑。
- **失败可见**：脚本失败时写 `backups/.last-backup-error`，成功时删掉它。
- `GET /api/system/backup`（需登录）读目录里最新的 `notes_blog_*.sql.gz`，
  超过 48 小时没成功 → `stale: true`；有失败标记 → 返回原文。
- 设置页新增「备份」区：最近成功时间（相对 + 绝对）、体积、份数，过期亮黄条，失败显示原因。
- 后端通过 `./backups:/data/backups:ro` **只读**挂载，只读文件元数据，不解析内容。

**两处与原计划的偏差**：
1. 原计划把状态塞进 `/api/health`。**改了**——`/api/health` 是公开接口，
   备份时间与目录属于运行信息，不该匿名可读；改成独立的、需鉴权的 `/api/system/backup`。
2. 顺手改了 `backup.sh`：容器模式下用容器自带的 `MYSQL_USER/MYSQL_PASSWORD`，
   **宿主机不再需要数据库密码**。否则定时任务要把密码写进 plist，那是更烂的选择。

**验收**：手工跑一次 → 设置页显示「8 分钟前 · 22.5MB · 4 份」；
写入失败标记 → 页面出现红字原因；未登录访问接口 → 401。

**遗留**：`launchctl bootstrap` 在自动化会话里会报 `Bootstrap failed: 5`，
**需要用户在自己的终端执行一次**（plist 已复制到 `~/Library/LaunchAgents/`）。

**工作量**：小（plist + 健康检查扩展一个字段）
**风险**：低。注意备份时间与 `mysqldump --single-transaction` 已经不会锁表。

**验收**：设置页显示"最近备份：x 小时前"；手工删掉标记文件后警告条出现。

### 5. `/api/ask` 与 `/api/search` 限流 — ✅ 已完成（2026-10-23）

**问题**：这两个接口每次调用都会消耗 LLM token（问答）或做向量检索（搜索）。
无限制意味着一个脚本就能把你的配额打满。

**实际做法**：
- `RateLimiter`：按 key 的**固定窗口**计数（不是滑动窗口——目的是防脚本，不是精确计费，
  维护每请求时间戳队列不值得）。问答 25 次/分钟、搜索 60 次/分钟，可按 IP 单独调。
  问答这一层**只对匿名调用者生效**：管理员不该被自己网站的限流卡住。
  `RATE_LIMIT_ASK` 必须 ≥ `GUEST_ASK_IP_DAILY_CEILING`（游客按 IP 的日上限），
  否则游客先撞「请 60 秒后再试」而不是「今天的次数用完了」。
- `RateLimitInterceptor` + `RateLimitConfig` 注册在 `/api/ask`、`/api/search`。
  **放在拦截器而不是 Controller 里**，因为拦截器在参数校验之前执行——
  否则「发一堆必然 400 的请求」就能绕开限流。
- 超限返回 **429 + `Retry-After`** + 中文文案，与登录限流一致。
- `ClientIp` 抽成公共类，登录限流与接口限流共用同一份「信任哪个头」的判断。

**踩到的坑**：`@WebMvcTest` 切片会加载所有 `WebMvcConfigurer`，但不会加载 `RateLimiter`，
于是 7 个控制器切片测试在启动阶段全挂。改成 `ObjectProvider` 获取、拿不到就跳过注册并 **warn**。

**后补的坑（2026-10-29，开放游客问答时才发现）**：`/api/ask` 返回 `SseEmitter` 属于异步请求，
容器在流结束时又派发一次（`DispatcherType.ASYNC`），`preHandle` 因此跑了两遍——
同一次提问被计两次，25 次上限第 14 次就拦，且第二次写 429 body 时响应已提交，
日志里一串 `IllegalStateException`。修法是只对 `DispatcherType.REQUEST` 计数
（`RateLimitInterceptorTest` 守着，去掉守卫即变红）。

**验收**：连发 11 次 `/api/ask`（空 body）→ 前 10 次 400、第 11 次 429 + `Retry-After: 52`。
顺便证明了「校验前计数」这条设计。

### 6. 健康检查扩展到依赖 — ✅ 已完成（2026-10-23）

**问题**：`/api/health` 之前返回的是写死的 `status: up`——数据库挂了它照样绿，
而 `scripts/deploy.sh` 正拿它判断部署成功。

**实际做法**：
- 检查 `db`（`select 1`，套 `completeOnTimeout` 1.5s）与 `ollama`（`GET /api/tags`，1s 超时）
- 有依赖不可用 → `status: degraded`，**HTTP 仍 200**：返回 5xx 会让编排层重启一个没问题的后端
- Ollama 不可用只降级不判死：浏览、编辑、发布都还能用，只有问答与语义检索受影响
- 设置页新增「运行状态」区，标出哪个依赖不可用以及**坏了会怎样**
- `deploy.sh` 改为读 `status` 字段，`degraded` 时列出不可用依赖并给出警告而不是打勾

**验收**：`docker compose stop ollama` → `{"status":"degraded","components":{"db":true,"ollama":false}}`，
同时 `GET /api/blog/stats` 仍是 200；启动 ollama 后恢复 `up`。

**踩到的坑**：配置键写错（`app.ollama.base-url`，实际是 `notes.ollama.base-url`），
后端启动直接崩。单元测试里 `OllamaProbe` 是 mock，抓不到这类错误。
已给 `@Value` 加默认值——**监控组件读不到配置时应该降级，而不是让应用起不来**。
